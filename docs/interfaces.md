# Interfaces and swap points

The "easy to replace any component" requirement is only credible if it's
concrete. Here's every deliberate boundary in Data Plant and what it costs
to swap.

| Layer | Interface | Default | Swap example | What changes |
|---|---|---|---|---|
| Storage format | Delta/Iceberg via Unity Catalog | Delta (UniForm-compatible with Iceberg reads) | Pure Iceberg + AWS Glue catalog | Table DDL + catalog config only; ingestion/transform code unchanged |
| Storage + compute (local dev) | Bronze: `deltalake` (delta-rs) tables on local disk; Silver/Gold: DuckDB via `dbt-duckdb` reading bronze through `delta_scan()` | Default for Phase 1 local iteration, no cloud account required | Databricks + Unity Catalog + S3 (see "Compute engine" row) | Swap `ingestion/batch/autoloader_job.py`'s `write_deltalake()` calls for Auto Loader `writeStream`, and `profiles.yml`'s `local` target for `databricks`; `sources.yaml`, the dbt SQL models, and `metadata/openlineage_emitter.py`'s call sites are unchanged |
| Compute engine | Spark on Databricks | Databricks jobs/clusters | OSS Spark on EMR, or Snowflake for the SQL layer | `infra/databricks` replaced by `infra/emr`; `ingestion/*` scripts are already plain PySpark so they mostly port as-is |
| dbt invocation (local dev) | `transform/run_dbt.py` wraps dbt-core's programmatic `dbtRunner` API | Reports one `PipelineRunEmitter` row per `dbt run` invocation | Bare `dbt run` CLI, or (cloud) a Dagster-triggered dbt Cloud/Databricks job | Cloud path emits metadata the same way a Databricks job step would -- wrap the job trigger with `start_run`/`end_run`, same as `run_dbt.py` does; the dbt project itself (`transform/dbt_project`) is unchanged either way |
| Orchestrator | Dagster asset graph | Dagster, local dev default: asset bodies call local Python functions directly (`ingestion/batch/autoloader_job.run_source()`, `transform/run_dbt.run_dbt_job()`) | Airflow DAGs; or, staying on Dagster, swap each asset body for a Databricks Jobs API call (`WorkspaceClient.jobs.run_now(...).wait_get_run_job_terminated_or_skipped()`) against jobs wrapping the same scripts on a real cluster | `orchestration/dagster_project` replaced for the Airflow swap; for the Databricks-jobs swap, only the four `@asset` function bodies in `assets.py` change -- the graph shape, schedule, and `PipelineRunEmitter` calls (made by the underlying scripts either way) are unchanged |
| Metadata sink | `PipelineRunEmitter` writing to a Delta table | Direct MERGE into `pipeline_runs` (Spark SQL on Databricks; delta-rs `DeltaTable.merge()` for local dev) | Real OpenLineage + Marquez server | Only `_write()` in `openlineage_emitter.py` changes; every call site (`start_run`/`end_run`/`fail_run`) stays identical |
| Wastage detection | `metadata/wastage_report.py` + `metadata/wastage_models/*.sql`, reading `pipeline_runs` + `table_reads` | Local dev: `table_reads` (`metadata/table_reads.py`) is populated from dbt's own `manifest.json` (real per-model dependency graph, parsed in `transform/run_dbt.py`) and from `serving/dashboard.py` logging gold-table views -- model/view-level granularity, but only for the two readers this project actually instruments; `input_tables`/`output_tables` remain a job-level fallback on top. Cost is `duration_seconds x LOCAL_DEV_HOURLY_RATE_USD`, a placeholder proxy | Cloud: populate `table_reads` from Databricks' real `system.query.history` instead -- catches *every* ad hoc BI/notebook read, not just the one dashboard this project knows about; cost from real DBU billing data | `unused_tables.sql`'s query is unchanged (it already reads from `table_reads`); only what populates that table changes. `estimated_cost_usd` becomes a real figure instead of a proxy, no schema change needed since the column already exists for this |
| Message broker | Kafka wire protocol | Redpanda (via `docker-compose.yml`) -- a real Kafka-protocol broker, not a mock; `kafka-python` talks to it exactly as it would talk to Apache Kafka | A managed Kafka (MSK, Confluent Cloud) or self-hosted Apache Kafka | Only `BOOTSTRAP_SERVERS` in `kafka_producer_clickstream.py` and `structured_streaming_job.py` changes; the wire protocol is identical so nothing else does |
| Stream processing | Reads Kafka, windows, merges into a gold table | Local dev: plain Python (`KafkaConsumer` + an in-process watermark buffer) merging into a Delta table via delta-rs, in `structured_streaming_job.py` | Spark Structured Streaming (`readStream`/`groupBy(window(...))`/`writeStream`) on Databricks, checkpointed to cloud storage | The whole body of `structured_streaming_job.py` is replaced; the topic (`kafka_producer_clickstream.py`) and the `PipelineRunEmitter` contract (one row per micro-batch, `job_type="streaming"`) are unchanged. The local version's tradeoff: watermark/window state lives in memory instead of a checkpoint, so it doesn't survive a restart -- acceptable for a bounded demo, not for a production streaming job |
| Vector store | `VectorStore` ABC | `PgVectorStore` | `DatabricksVectorSearchStore` | Add one class in `ai_rag/vector_store.py` implementing `upsert`/`query`; `ingest_embeddings.py` and `chatbot.py` don't change |
| Embedding provider | `embed_texts()` / `embed()` functions | Local dev: Ollama's `nomic-embed-text` (768-dim, no API key, no cloud spend) via its OpenAI-compatible `/v1/embeddings` endpoint -- same `openai` client already in requirements.txt, just pointed at `localhost:11434` | OpenAI `text-embedding-3-small` (1536-dim), or any other embedding API | One function body per file; also update `PgVectorStore`'s `dims` to match the new model's output size and re-ingest (embeddings from different models aren't comparable, so switching providers means re-embedding the corpus, not just swapping a client) |
| Chatbot LLM | Chat completion call | Local dev: Ollama's `llama3.2:3b`, same OpenAI-compatible endpoint | OpenAI `gpt-4o-mini`, or any other LLM API (incl. Claude) | One client call in `ai_rag/ask.py` / `chatbot.py`; the retrieval and (for `chatbot.py`) SQL-vs-doc-search routing logic is provider-agnostic. Tradeoff: a 3B local model answers correctly but is noticeably less consistent about following formatting instructions (e.g. inline citations) than a hosted model -- `ask.py` prints retrieved sources itself rather than trusting the model to always mention them |
| BI/serving | Reads gold tables, no upstream write path | Local dev: `serving/dashboard.py`, a small Streamlit app querying DuckDB (`main_gold.daily_revenue`) and the streaming Delta table (`gold_streaming/session_activity_1min` via `delta_scan()`) directly, each through its own short-lived connection so the dashboard can't hold a lock that blocks a batch write | Databricks SQL warehouse + dashboards (cloud target); locally, a real BI tool instead of hand-rolled Streamlit -- **Rill** (single binary, official local-DuckDB-file connector, most BI-tool-like for the least new toolchain) or **Apache Superset** (official DuckDB engine spec, closest fidelity to a real Databricks SQL dashboard, heavier to stand up: its own metadata DB + Redis + workers via `docker-compose`). Metabase and Grafana were compared too but fit worse here -- Metabase's DuckDB driver is an unofficial community plugin, and Grafana's panel types skew toward time-series/ops monitoring rather than business-style charts | Serving layer only reads gold tables; no upstream change needed either way. Any tool that holds a persistent connection to `warehouse.duckdb` (a BI tool's connection pool, a long `dagster dev` session, etc.) will conflict with a concurrent writer -- DuckDB allows many readers but a writer needs the file exclusive; Streamlit sidesteps this by opening/closing per query instead of pooling |

The pattern throughout: **every component talks to the next one through a
narrow interface it owns, never reaches past it.** Ingestion doesn't know
about Dagster. Dagster doesn't know how jobs compute, only that they run
and report status. The chatbot doesn't know if `PgVectorStore` is backed by
Postgres or something else. That discipline is what makes the swap claims
true instead of aspirational.
